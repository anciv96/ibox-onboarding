# Sales Doctor — платформа онбординга менеджеров

Веб-платформа для самостоятельного онбординга новых менеджеров по продажам
в компании Sales Doctor (продают IBOX — систему складского учёта). Новичок
проходит модули по ссылке-приглашению без участия руководителя, сдаёт
финальный тест; руководитель (админ) проверяет и решает: допущен / на
доработку / отказ.

## Стек
- Python 3.13 + Django 6.1
- SQLite локально, Postgres в проде (через `dj-database-url` + `DATABASE_URL`)
- Django-шаблоны + Tailwind CSS через CDN (без сборки/Node)
- Встроенная Django admin — это и есть панель администратора, оформленная темой
  `django-unfold` (Tailwind, фирменный `#2663EB`); см. раздел «Тема админки» ниже
- `python-decouple` для переменных окружения, `whitenoise` для статики,
  `markdown` + `bleach` для безопасного рендера конспектов модулей

## Структура приложений
- **accounts** — `Invitation` (именные ссылки-приглашения) и `Student`
  (профиль ученика: статус, прогресс, итоговый балл, заметка админа)
- **onboarding** — `Module`, `ModuleQuestion`, `ModuleAnswerOption`,
  `ModuleProgress` (факт прохождения), `ModuleAttempt`/`ModuleAttemptAnswer`
  (лог каждой попытки), бизнес-логика в `onboarding/services.py`
- **finaltest** — `FinalTestItem` (mcq/open/case), `FinalTestOption`,
  `FinalTestSubmission` (одна попытка, их может быть несколько),
  `FinalTestAnswer`; бизнес-логика в `finaltest/services.py`
- **core** — общие шаблоны/статика (пока пусто, наполнится на Этапе 4)

## Ключевые решения (зафиксировано с пользователем)

1. **AI-оценка финального теста отложена.** В модели `FinalTestAnswer` есть
   поле `ai_score` — заготовка на будущее. Сейчас открытые ответы и кейсы
   читает и оценивает админ вручную через Django admin (поля `ai_score` и
   `admin_comment` редактируемые, но не заполняются автоматически).

2. **Приглашения — именные ссылки.** `Invitation.full_name` задаётся
   заранее админом, `token` (UUID) — часть URL. Страница регистрации по
   токену будет на Этапе 2 (`accounts:register`, ещё не реализована —
   в админке это явно указано).

3. **Модуль засчитывается только при 100% правильных ответов** на
   контрольные вопросы (см. `onboarding.services.submit_module_attempt`).
   Каждая попытка (успешная и нет) логируется в `ModuleAttempt`, чтобы
   админ видел, сколько раз ученик пытался. Один неверный ответ = модуль
   не засчитан, но ученик может пересдать сразу же.

4. **Финальный тест допускает пересдачу.** Правило в
   `finaltest.services.can_start_final_test`: тест доступен, если это
   первая попытка (все модули пройдены), либо статус ученика —
   `needs_rework` (админ явно отправил на доработку). Все попытки
   (`FinalTestSubmission`) хранятся, а не только последняя — админ видит
   полную историю пересдач в карточке ученика.

5. **Статусы ученика** (`Student.Status`): `in_progress` → после отправки
   финалки автоматически `pending_review` → админ вручную ставит
   `approved` / `needs_rework` / `rejected`. `needs_rework` — единственный
   статус, который открывает пересдачу.

6. **Дизайн**: база — нейтральная палитра (серый/белый/тёмный текст),
   единственный акцент — `#2663EB` (цвет логотипа). Наполнение на Этапе 4.

7. **i18n (русский + узбекский)**: `LANGUAGES = [ru, uz]`, `LocaleMiddleware`,
   `LANGUAGE_CODE = 'ru'`, переключатель RU/UZ в шапке (`django.views.i18n.set_language`,
   выбор хранится в cookie год). Исходный язык строк в коде — русский (msgid =
   русский текст), поэтому для `ru` перевод не нужен, для `uz` — `locale/uz/`.
   Узбекская латиница. **Переводы написаны Claude — нужна вычитка носителем.**
   Контент курса двуязычный через необязательные поля `*_uz`
   (`Module.title_uz/youtube_id_uz/text_content_uz`, `ModuleQuestion.text_uz`,
   `ModuleAnswerOption.text_uz`, `FinalTestItem.prompt_uz`, `FinalTestOption.text_uz`);
   в шаблонах используются свойства `l_title`, `l_text`, `l_prompt` и т.д.
   (`core/i18n.localized`): узбекская версия, если выбран uz и поле заполнено,
   иначе русская. Ответы стажёров (открытые вопросы/кейсы) хранятся как есть,
   админ читает их и оригиналы вопросов по-русски.

8. **⚠️ SQLite и деплой.** Render/Railway имеют эфемерную файловую систему
   между деплоями — SQLite-файл может обнулиться. `settings.py` уже читает
   `DATABASE_URL` через `dj-database-url` (по умолчанию — локальный SQLite).
   На Этапе 5 в проде обязательно подключить Postgres через `DATABASE_URL`,
   иначе есть риск потери данных учеников.

## Как задуманы модели доступа (для будущих сессий, если контекст потерян)

- `onboarding.services.is_module_unlocked(student, module)` — модуль N
  доступен, если N==1 (по `order`), либо для модуля N-1 есть
  `ModuleProgress`.
- `finaltest.services.can_start_final_test(student)` — см. решение №4 выше.
- Итоговый балл (`Student.final_score`) — админ выставляет вручную после
  чтения всех ответов; автоматически считается только mcq-часть
  (`FinalTestSubmission.mcq_score_percent`), она видна как подсказка.

## Тема админки (django-unfold)

- Подключена в `INSTALLED_APPS` **перед** `django.contrib.admin`; конфиг —
  словарь `UNFOLD` в `config/settings.py` (цвета, боковое меню с группами
  «Стажёры / Контент курса / Система», красный счётчик работ на проверке).
- Все админ-классы наследуются от `unfold.admin.ModelAdmin` / `TabularInline` /
  `StackedInline`; `User` и `Group` перерегистрированы в `accounts/admin.py`
  (иначе остались бы в старом стиле). Действия — `unfold.decorators.action`,
  цветные статусы — `@display(label={...})` (метод возвращает пару
  `(ключ, текст)`).
- Главная админки — свой шаблон `templates/admin/index.html` + колбэк
  `config/dashboard.py` (карточки-счётчики, «Ждут проверки», «Сейчас учатся»,
  кнопка «Пригласить стажёра»). Логотип в шапке подхватывается из
  `static/logo.png`, если файл есть.
- Кнопки решения «Допустить / На доработку / Отказ» — `actions_detail`
  в `StudentAdmin` (один клик из карточки ученика; `warn_unsaved_form`
  предупредит, если в форме есть несохранённые правки — кнопки решения
  НЕ сохраняют балл/заметку, для них нужна обычная кнопка «Сохранить»).
- Свои HTML-вставки (ответы теста, кнопка копирования ссылки) используют
  только inline-стили: Unfold содержит лишь те tailwind-классы, что нужны
  ему самому, и не знает CSS-переменных старой админки.
- **Переводы**: у Unfold нет русской локали. Недостающие строки лежат в
  `locale/ru/LC_MESSAGES/django.po`, скомпилированный `django.mo` закоммичен
  (на сервере `gettext` не нужен). Чтобы добавить строки: `makemessages` →
  дописать переводы → `msgfmt -o django.mo django.po`.

## Ученический интерфейс: дашборд, язык, тёмная тема

- **Дашборд** (`/`, `onboarding/dashboard.py::build_dashboard` +
  `onboarding/templates/onboarding/dashboard.html`): приветствие с кольцом
  прогресса, карточки (модулей пройдено, точность ответов по всем попыткам,
  «с первой попытки», дней в обучении), «Путь обучения» (модули + финальный тест
  как последний шаг, бейджи попыток, история сдач финалки с % части А),
  карточка статуса, лента активности. Ученик НЕ видит `final_score` и
  `admin_note` — только статус и авто-результат части А.
- Логика вынесена в `build_dashboard` и покрыта тестами (`DashboardBuilderTests`);
  порядок разблокировки там продублирован «пакетно» — есть тест на совпадение
  с `is_module_unlocked`.
- **Тёмная тема**: Tailwind `darkMode: 'class'`, класс `dark` на `<html>` ставится
  скриптом в `<head>` до отрисовки (без мигания) из `localStorage['theme']` либо
  по `prefers-color-scheme`; кнопка-переключатель в шапке. Общие стили —
  компонентные классы (`.card`, `.btn-primary`, `.link`, `.muted`, `.option` …)
  в `<style type="text/tailwindcss">` в `templates/base.html` — новые страницы
  стилизуем ими, тогда тёмная тема работает автоматически.
- **Как добавлять/менять строки перевода**: обернуть текст в `{% trans %}` /
  `_()`, затем `python manage.py makemessages -l uz --ignore=venv --ignore=staticfiles
  --ignore='*/migrations/*' --no-location`, дописать `msgstr` в
  `locale/uz/LC_MESSAGES/django.po`, скомпилировать `msgfmt -o
  locale/uz/LC_MESSAGES/django.mo locale/uz/LC_MESSAGES/django.po`. Файл `.mo`
  коммитим (на сервере gettext не нужен).
- Ловушка: в функции, где используется `_()` из gettext, нельзя писать
  `a, _, b = x.partition(...)` — переменная `_` затенит перевод (уже исправлено
  в `accounts.views.register`).
- Ловушка тестирования UI: снимки браузера после прокрутки на эмулированном
  мобильном экране показывают пустые области — это артефакт инструмента, не баг
  страницы; для проверки увеличивать высоту окна, чтобы страница влезла целиком.

## Сохранение ответов (автосохранение черновиков)

- **Сервер — источник правды.** `ModuleDraft` (черновик квиза модуля) и
  `FinalTestSubmission.draft` (черновик финального теста, живёт в открытой
  попытке). Каждое изменение (радиокнопка/текст) уходит на сервер через ~0,5 с:
  `POST /modules/<id>/draft/` и `POST /final-test/draft/` (JSON
  `{"answers": {id: значение}}`, CSRF-заголовок `X-CSRFToken`, обёртка
  `core/http.json_draft_endpoint` — при потере сессии отдаёт JSON 401, а не редирект).
  Клиент шлёт ПОЛНОЕ состояние, сервер заменяет черновик целиком (очищенное поле
  тоже очищается).
- **Восстановление рисует сервер** (отмеченные радио и текст в `<textarea>`
  вставляются при рендере страницы) — работает после обновления, закрытия вкладки
  и на другом устройстве, без участия JS.
- **Валидация**: `onboarding.services.clean_module_answers` /
  `finaltest.services.clean_final_answers` отбрасывают чужие/выдуманные id,
  тексты режутся до 10 000 символов.
- **Обрыв связи**: `static/js/autosave.js` при ошибке кладёт копию в
  `localStorage` (`quiz-pending-…` / `finaltest-pending-…`), ретраит с
  нарастающей паузой и по событию `online`; при следующем открытии страницы
  недосланное применяется к форме и отправляется. Успешная отправка стирает копию.
  При закрытии/сворачивании вкладки несохранённое шлётся сразу (`keepalive`).
  Пока есть недосланное — браузер спросит подтверждение при закрытии вкладки.
- **Проверка ответов модуля — POST → redirect → GET** (PRG): обновление страницы
  после неверной попытки больше не пересылает форму и не плодит лишние попытки.
  Выбор после ошибки остаётся черновиком; «Неверно» горит у вопроса, пока ученик
  не поменял ответ (вычисляется по последней неудачной попытке + черновику).
  Успешная попытка / отправка финала очищают черновик.
- Индикатор состояния (`templates/partials/save_status.html`): «сохраняется
  автоматически» → «Сохраняем…» → «Сохранено 14:05» / «Черновик восстановлен» /
  «Нет связи…» / «Не удалось сохранить…»; тексты переводятся (ru/uz).
  Кнопки отправки блокируются после нажатия (защита от двойного клика).
- Ограничение: если один ученик одновременно правит ответы на двух устройствах,
  побеждает последнее сохранение (слияния нет).
- Дашборд показывает «Есть сохранённые ответы — можно продолжить».

## Публичный тест с ноутбука (ngrok)

`scripts/public.sh start|stop|status|url` — gunicorn на 127.0.0.1:8001 (`DEBUG=False`,
отдельная `db_public.sqlite3`, `SECRET_KEY` в `.env.public`) + `ngrok http 8001`.
Все локальные файлы игнорируются git (`.env.public`, `db_public.sqlite3`,
`.public_admin_password`, `logs/`). `seed_demo_data --content-only` создаёт только
модули и финальный тест, без админа с известным паролем и демо-учеников. Для
работы за туннелем в `ALLOWED_HOSTS`/`CSRF_TRUSTED_ORIGINS` прописаны домены
`*.ngrok-free.app/.dev`, `*.ngrok.app/.dev/.io` (свой домен — переменная `EXTRA_HOST`).
Нюанс: ngrok 3.18 отвергается аккаунтом (ERR_NGROK_121, нужен ≥3.20) — лечится
`ngrok update`. Ссылки-приглашения строятся от текущего адреса в браузере
(`location.origin`), так что при смене адреса нужно выдать новые.

## Обучение и тест модуля — два разных этапа (решение с руководителем)

Логика разделена: сначала **обучение**, и только потом **проверка знаний**.
- `ModuleStep` — шаг обучения внутри модуля (`kind`: video / text / action
  (практическое задание) / resource (ссылка)); поля `is_required`,
  `requires_note` (для action: без короткой заметки отметить нельзя), `*_uz`.
  Админ собирает шаги инлайном в карточке модуля. Видео и конспект больше НЕ поля
  `Module` — миграции `0005–0007` перенесли их в шаги и удалили старые поля.
- `StepProgress` — отметка ученика (`is_done`, `done_at`) и заметка. Ученик сам
  ставит галочки (решение: без YouTube API и без подтверждения наставником);
  админ видит отметки и заметки в карточке ученика.
- Страницы: `/modules/<id>/` — обучение (шаги + прогресс + кнопка «Проверить
  знания»), `/modules/<id>/quiz/` — тест модуля (отдельная страница; логика
  прежняя: 100% верных, попытки, автосохранение, PRG). Тест открывается, когда
  выполнены все ОБЯЗАТЕЛЬНЫЕ шаги (`services.is_quiz_unlocked`; модуль без шагов —
  тест открыт сразу). Гейт стоит во вьюхе (GET и POST редиректят на обучение).
- Отметка шага — `POST /modules/<id>/steps/<step_id>/` (JSON `{done?, note?}`,
  обёртка `core/http.json_student_endpoint`); ответ 422 `note_required` — нужна
  заметка. Стёртая заметка снимает отметку. Скрипт — `static/js/steps.js`.
- Дашборд: у текущего модуля «Шаги обучения: N из M».
- Финальный экзамен пока прежний (этап 2 запланирован): отдельный раздел, таймер
  (по умолчанию 45 мин, настраивается в админке), 1 попытка, перемешивание вопросов и
  вариантов, счётчик уходов со вкладки (виден админу), пересдача только через
  «На доработку».
- Ловушка перевода: `makemessages` подставляет в новые строки чужие «похожие»
  переводы с пометкой `fuzzy` — их нужно перевести явно и снять флаг (иначе в
  интерфейсе останется/уйдёт не то). Для склонения по-русски (`blocktrans count`)
  нужен русский каталог с тремя формами (`locale/ru`).

## Оформление обучения, порядок, прогресс и значки

- **Фирменный цвет в интерфейсе ученика**: шапка сайта `bg-brand-600` (`dark:bg-brand-700`),
  баннеры модуля/теста и приветствие на дашборде — градиент `brand-600 → brand-800`
  с белым текстом (компонентный класс `.btn-light` для кнопок на цветном фоне).
- **Шаги как «путь»** (`module_detail.html`): у каждого шага крупный круг с номером
  (нумерация автоматическая, `forloop.counter`). Состояние считает `services.steps_state`
  (`done` / `current` = первый невыполненный / `upcoming`) и пишет в `data-state`:
  выполненные свёрнуты с зелёной галочкой, текущий раскрыт и обведён брендовой рамкой,
  следующие приглушены. `static/js/steps.js` (`refreshStates`) после отметки сворачивает
  шаг, раскрывает следующий и плавно прокручивает к нему. Раскрыть любой шаг можно кликом.
- **Порядок автоматический**: `order` по умолчанию 0; при сохранении `next_order()`
  (`core/ordering.py`) ставит следующий номер (у шагов и вопросов — в пределах модуля,
  у модулей и вопросов финала — глобально). В админке шаги и вопросы модуля
  перетаскиваются (Unfold `ordering_field` + `hide_ordering_field`), вопросы финального
  теста — перетаскиванием в списке; у Module поле `order` остаётся видимым (уникальное).
  Ловушка Unfold: поле с `ordering_field` нельзя ставить в одну строку fieldsets с
  другим полем — скроется вся строка.
- **Общий процент онбординга** — одна функция `onboarding.progress.overall_progress`
  (обязательные шаги + тест каждого модуля + финальный экзамен, засчитывается при
  отправке). Её же используют шапка (`core.context_processors.onboarding_progress`,
  процент + полоска, обновляются «вживую» через ответ `/steps/` → `overall_percent`),
  кольцо на дашборде, `Student.progress_percent` и админка.
- **Значки** (лёгкая геймификация): на дашборде карточка «Значки» — медаль за каждый
  пройденный модуль и звезда «Допуск» при статусе «допущен». Без очков и рейтингов.

## Геймификация и контент (зафиксировано)

- Онбординг для **сейлзов**, не для колл-центра/техподдержки: нужны базовые
  функции iBox и умение понять, подходит ли бизнес клиента. Без деталей.
- Контент (модули 1–7, все опубликованы) лежит в `db_public.sqlite3`; модуль 7
  «Подходит ли iBox клиенту?» — бизнес-кейсы («головоломки») со сценарными
  вопросами. Непроверенные утверждения помечены невидимым `<!-- ЧЕРНОВИК -->`.
  `seed_demo_data` по-прежнему создаёт старый демо-контент (только dev-БД).
- XP/ранги/серия/достижения считаются на лету из существующих данных
  (`onboarding/gamification.py`), отдельных таблиц нет: шаг 10 (действие 20),
  тест модуля 50 + 25 за первую попытку, финал 100. Ранги — доли от
  максимума: 0/.10/.30/.55/.80/1.0 (Новичок … Мастер iBox).
- `ModuleStep.needs_note` — заметка обязательна только для шагов-действий,
  даже если `requires_note` включён у материала.
- Тесты: 97 проходят. Финальный экзамен (таймер, 1 попытка, перемешивание,
  счётчик выходов из вкладки) — Этап 2, ещё не сделан.

## Финальный тест: банк вопросов и случайная выборка

- В `FinalTestItem` лежит банк (сейчас 118 mcq + 4 открытых, всё с узбекским
  переводом). При старте попытки `finaltest.services.pick_item_ids` берёт случайные
  `FINAL_TEST_MCQ_COUNT` (17) закрытых и `FINAL_TEST_OPEN_COUNT` (3) открытых
  вопросов (settings/env) и сохраняет их в `FinalTestSubmission.item_ids`;
  порядок вариантов у каждой попытки свой, но стабильный (`shuffled_options`).
  Черновик и проверка ограничены вопросами именно этой попытки.
- Открытые вопросы — бизнес-кейсы на знание программы, не «навыки продаж».
  Правильный ответ mcq — всегда ровно один; в кейсах допустимы частично верные
  варианты, верный — самый полный/точный.
- Вопросы модулей — по 6 на модуль, сложные сценарные; правильные ответы
  раскиданы по позициям. Банк можно править в админке.

## Docker + перенос между серверами

`Dockerfile` + `docker-compose.yml` (db=Postgres 16 с томом `pgdata`,
web=gunicorn, caddy=TLS-прокси, авто-HTTPS по домену из `.env`/`Caddyfile`).
Данные живут только в томе `pgdata`, не в образе — сервер можно менять без
потери данных: `scripts/docker_backup.sh` (`pg_dump` → `backups/docker-db-*.sql.gz`,
хранит 14 копий) и `scripts/docker_restore.sh` на любом сервере с тем же
compose-файлом. Подробный порядок первого запуска и переноса — «Вариант C» в
`DEPLOY.md`. Whitenoise отдаёт статику из самого Django-контейнера, отдельный
nginx не нужен. Собрать образ локально не удалось проверить (Docker в этой
среде недоступен) — первую сборку стоит проверить на сервере.
